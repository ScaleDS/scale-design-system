Agents

Point your coding agent at Scale and it stops guessing. Every component and foundation ships a guidance file written for machines.

Each one is generated from the page you are reading now, so what an agent is told and what you see cannot drift apart.

What you get

Three layers, each doing a different job.

Layer What it is Why it matters Guidance files One Markdown file per component and foundation, 70 in all The contract and the judgment in one place: every prop with its accepted values, plus when to use the component, when not to, and its accessibility rules MCP server Bundled with the package, serves those files on request Your agent reads one component at a time instead of pulling a 100KB catalog to place a single button Skills Procedures the agent follows: build, review, migrate A server answers questions but changes nothing on its own. The skills are what make an agent look things up in the first place

The third layer is the one people skip, and it is the one that does the work. An agent with the server installed and nothing telling it to use them will still write a raw <button> with a hardcoded colour.

Install

In Claude Code, one plugin brings the skills and the server together.

Restart Claude Code, then check it landed with /plugin. You should see scale enabled, and the scale-build, scale-review and scale-migrate skills available.

Point your agent there, or at the published copies. Every page on this site serves its guidance at <page-url>agent.md, indexed at /llms.txt.

All three routes return the same file, so nothing here depends on one vendor.

Try it

Ask for what you want in plain language. Naming components is not necessary, and naming them wrongly is the thing the guidance is there to prevent.

Build something

Expect sc-section-pricing with sc-card-pricing children, spacing from --sc-space-*, and no colour literals. The agent checks the pattern library before assembling anything from parts.

Let it pick the right component

Expect sc-toast, not sc-alert. The distinction is written into both components’ guidance, so the agent reads it rather than guessing from the names.

Watch it avoid a trap

Expect sc-button-icon with a label on each control. sc-button’s guidance says outright not to use it for icon-only actions, and the accessibility rules require the accessible name.

Style something by hand

Expect semantic tokens throughout and no hex values. A literal that looks right in one theme breaks the other, which is why hardcoded colour is the failure the guidance works hardest to prevent.

Review code you already have

Point the review skill at existing work. It audits rather than rewrites, so you decide what gets fixed.

It checks five things:

  • Raw HTML controls where a Scale component exists
  • Hardcoded colours, spacing, type and motion that have tokens
  • Prop values outside a component’s accepted set
  • Accessibility contracts the code does not meet
  • Missing imports

Findings come back ordered by severity, with the token or component you should have used named for you.

Most of these fail quietly. An invalid prop value renders the default instead of throwing, so nothing surfaces at runtime and the page just looks slightly wrong.

Migrate an existing page

Moving from Tailwind, Bootstrap or plain CSS works one piece at a time.

The agent inventories every control first and shows you the mapping before editing anything. Whatever has no Scale equivalent comes back as a list, because that is a decision for you rather than something to improvise.

What to expect

The difference is measured, not asserted. Thirty realistic prompts, graded for hardcoded values, raw HTML where a component exists, hallucinated tags and invalid prop values:

Setup Clean output Problems found No guidance 37% 161 Skills and catalog 57% 26 Skills, catalog and lookup 93% 3

Being able to look a component up is where most of the gain sits. Invalid prop values drop from 15 to none once the agent can read the accepted values instead of inventing them.

Treat the numbers as a large effect rather than a precise one. Repeat runs move by several points, and this was measured through a coding agent rather than a bare model.

Keeping it honest

You never edit a guidance file. Each one is generated from the page it documents, so the agent version and the human version are the same content by construction, and a build fails if they fall out of step.

That matters because hand-written agent instructions rot. A prop changes, the documentation is updated, the agent file is forgotten, and your tooling confidently recommends something that no longer works.
